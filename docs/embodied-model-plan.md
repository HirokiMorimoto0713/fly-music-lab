# 身体を持つハエの検討

2026-09-17。ユーザーの優先方向は「物理的な身体で歩いたり飛んだりするハエ」。調査と初期計画の記録です。この後、第一段階の手動歩行を `walk.html` に実装し、Chromeで検証しました。実装済みの操作と境界は [歩行ガイド](walking-guide.md)、実測値は [検証記録](verification.md) を参照してください。脳と飛行の接続は未実施です。

## 推奨する順序

1. NeuroMechFlyのブラウザ用MuJoCo実装で、平地の前進・旋回・停止を再現する。
2. 現在のMaleCNSの神経出力を歩行コントローラーへ接続し、手動操作と比較する。
3. 身体の位置・接触などを人工的な感覚入力へ戻し、閉ループで比較する。
4. FlyBodyの公式飛行環境と学習済みコントローラーを単独で再現する。

歩行の最初の身体はNeuroMechFlyです。FlyBodyとは身体モデルが異なります。両方の挙動を同一モデルの能力として扱いません。歩行から離陸して飛行へ移る制御は初期範囲に含めず、まず別実験として検証します。

## 候補の役割と選定理由

| 候補 | 確認できたもの | 今回の位置づけ |
| --- | --- | --- |
| NeuroMechFly / FlyGym 2.1 | MuJoCoの身体、接地、歩行制御、ブラウザ用WASM実装 | 最初の歩行実験。既存の静的Web配信に合わせやすい |
| FlyGym上のFlyBody | FlyBodyの身体と左右2入力の歩行・旋回サンプル | 身体を比較する第2候補。公式が実験的対応と記載 |
| TuragaLab/flybody | MuJoCoの身体、歩行・飛行・視覚誘導飛行、配布された制御モデル | 飛行の第一候補。Python環境で単独再現してから接続 |
| flyvis | 視覚回路の刺激応答モデル | 歩行成立後の視覚入力候補。身体を動かす初期要件には含めない |
| Eonの統合例 | 下行性神経の出力を少数の運動制御信号へ変換する説明 | 接続の参考。公開fly-brainリポジトリのREADMEは脳計算が中心で、身体統合をそのまま再現できるとは確認できていない |

NeuroMechFlyのブラウザ実装はMuJoCoをWASMで実行し、制御器をJavaScriptへ移植しています。CPG（脚のリズムを作る発振器）と事前に用意された脚の軌道が関節の目標角を作り、接地や身体運動をMuJoCoが計算します。実配線の全脳モデル自体が歩き方を学習したものではありません。

FlyGymのFlyBody歩行例は42個の位置制御アクチュエーターを使います。関節順序の変換が必要で、接着制御は不安定な挙動を理由に無効化されています。最初から標準モデルと同等の対応を前提にしません。

## 今のアプリとの接続案

```text
目印・接触などの入力
    ↓ 人工的な符号化
MaleCNSの固定LIF計算
    ↓ DNa02左右・DNp09の測定値
左右の歩行指令へ変換
    ↓
脚のリズムと姿勢の制御器
    ↓ 関節の目標角・接着の指令
MuJoCoの物理的な身体
    ↓ 実際の位置・向き・接触
次の入力へ戻す
```

現行の `src/talk-model.js` はDNa02左右とDNp09の測定から旋回・前進を読み出しています。まずこのインターフェースを候補にし、左右信号と実際の旋回方向を手動試験で校正します。発火率から制御値への尺度、飽和、停止条件は記録します。ユーザー文や目印の正解方向を脚へ直接渡して、神経出力を迂回する実装にはしません。

脳の20 msごとの集計と、ブラウザ版MuJoCoの0.1 ms刻みをシミュレーション時刻で同期します。描画のフレーム時刻は制御の時計にしません。初期実験では脳の1区間の指令を身体側の対応する区間だけ保持し、身体の実際の姿勢から次の入力を作る方式を検証します。非同期Worker間の処理速度、停止とリセットは要検証です。

現行のお絵かきは観測ごとに神経状態を初期化しています。運動の閉ループでは、その処理をそのまま使わず、状態を保持する会話側の構成を参考にします。

## 最初の試作で観察するもの

画面は、物理的に歩くハエ、左右の制御入力、脚の接触、軌跡、神経の測定値を並べます。手動操作と脳の出力による操作を切り替えて、どの段階が運動を作っているかを確認できるようにします。

採用の判定条件:

- 固定版の身体・制御器・初期条件から、少なくとも物理時間2秒をNaNや計算破綻なく進める。
- 前進、左右の旋回、停止の各指令について、身体の変位・向き・接触を記録する。停止直後の慣性と、指令を出し続けている状態を区別する。
- 同じ条件の再実行を比較し、数値差の許容範囲を実測から定める。
- 脳をつないだ際は、手動指令・通常の神経出力・伝播なし・感覚入力なしを区別する。ゼロ指令でも転倒や重力による変化は起こりうるため、「身体が完全に静止する」を無反応の条件にしない。
- 同期したログから、入力・神経出力・脚への指令・身体の結果を追える。
- 実時間倍率、描画fps、読み込み量、メモリを測定する。最初はスロー再生を許容し、リアルタイム動作を先に約束しない。

## 実行環境と配信

母艦はAMD Ryzen 7 8745H、メモリ約29 GiB、Python 3.12.3。調査時に `nvidia-smi` は見つかりませんでした。専用NVIDIA環境を前提にせず、CPUと既存Chromeで確かめます。

FlyGym 2.1のPython要件は3.12以上3.15未満で、母艦のPythonは範囲内です。ブラウザ版は実行時にPythonを要求しません。ただし配布モデルの生成と固定、現行Three.js 0.186.0と公式例の0.169.0の分離、WASMと全脳計算の同時実行性能は未検証です。初期試作は別ページ・別モジュールで構成し、既存4機能の依存を差し替えません。

FlyBodyの学習済み制御モデル用依存はTensorFlow 2.8.0等の旧構成です。PyPIのTensorFlow 2.8.0配布wheelはPython 3.7〜3.10向けで、3.12向けはありません。公式構成を再現する際は独立したPython 3.10環境を候補にします。制御モデルのCPU推論、描画バックエンド、性能はまだ動作確認していません。

FlyBodyの配布データは、制御モデル約6.54 MB、飛行データ約12.88 MB、歩行データ約3.02 GBと分かれています。全データを最初から取得せず、使う実験に必要なものだけを取得する計画です。Figshare記事のライセンス表示はGPL 3.0+、flybodyコードはApache-2.0であり、再配布時に出典と適用範囲を別々に確認します。

ブラウザ歩行は現在のGitHub Pagesへ追加できる構成が有望です。FlyBodyのPython推論を公開する場合は別の計算サービスかブラウザ移植が必要で、現時点では配信方式を確定していません。

## 今回実際に確認した範囲

公式の [NeuroMechFlyブラウザゲーム](https://neuromechfly.org/wasm/game/game.html) を、母艦のheadless Chrome / SwiftShaderで開き、開始、W入力、画面描画を確認しました。pageerrorは0件、終了付近の表示は14 fps、0.08倍速、接触6箇所でした。これはハードウェア描画を使うMacや通常のChromeの性能を示す値ではありません。

ゲームは公式設定で約0.1倍速を目標にしています。HUDのタイマーは制御用の時間表示で、今回の0.60→6.01という変化を物理シミュレーション6秒と解釈しません。身体の内部座標・力の精度や、飛行は未検証です。

結果: `artifacts/neuromechfly-browser-probe.json`。画面: `artifacts/neuromechfly-game-ready.png` と `artifacts/neuromechfly-game-walk.png`。新しい依存はインストールしていません。
